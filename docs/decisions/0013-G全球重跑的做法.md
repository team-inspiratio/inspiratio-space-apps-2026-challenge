# 0013 阶段 G：全球重跑的做法

## 背景

任务卡 `G-global` 要求：把区域配置换成全球（新建配置，不改冻结的 `config/regions.json` 和 settings），用冻结的模型设置重跑格子化之后的流程（训练上线版、生成序列、稳定性区间、导出），用同一判卷机器按 GFED 区报告验证窗口分数，再发布全球数据集。不准重新挑模型，不准重考测试集。

用户 2026-11-03 同意扩展到全球，并授权 AI 决定技术细节、写成记录。下面各条都在**看任何全球分数之前**写定。代码在 `harmonization/global_grid.py`、`harmonization/series_global.py`，全球配置在 `config/regions-global.json`。

## 1. Git：怎么接着开 PR

- **理由**：

- 合并后护栏检查 0 违规（冻结清单历史只增不改）。

## 2. 全球范围（`config/regions-global.json`）

- **格子**：满足任一条件的 0.25° 格子都纳入，共 278,192 个：
  - GFED4.1s 基础分区编码不为 0（陆地）；
  - 2000-11 至 2026-10 有过任何一颗卫星的清洗后火点；
  - 落在任何评分矩形里（这样每个矩形都完整）；
  - 落在 `config/regions.json` 的六个框里（这样 v1 的六个区完整）。
- **区域**：用 GFED4.1s 的 14 个基础分区。海洋格子（编码 0）归到最近的陆地格子所在的区。
- **留出区**：三个留出框照 `config/regions.json` 不变，单列为区域，`role = holdout`。它们没有 VIIRS 列，不参与训练和评分，序列每个月都是模型估计。其余格子 `role = train`。
- 只读冻结的 `regions.json`，不改它；`regions-global.json` 不冻结。

## 3. 模型：冻结设置，在全球训练格子上重训（按任务卡）

- **上线版**：
  - E028，参数和轮数（766 / 970）全部取自 `results/freeze.json`；
  - 在全球训练格子（`role = train`）的 2014-01 至 2021-06 可用格子-月份上重训；
  - 不重新调参（不跑 Optuna），也不重新早停。
- **验证窗口**：各用该窗口自己冻结的配置（`freeze.json` 的 `validation_windows`），和 S12 `terra-check` 做法相同。
- **和 S11 的关系**：S11 的测试成绩属于只用 3 个示范区训练的评估版，全球版没有测试成绩，数据说明里写明。
- **为什么不直接把 S11 模型套到全球**：任务卡写的是“重跑训练（上线版）”，计划第 2 节写的是“换成全球配置重跑一遍”。冻结代码在全球配置下（`freeze.training_table`）本来就会用全部训练格子。另外，测试 2 已经说明只用 3 个区训练、在新生态区会偏差很大（留出区 MALE 0.644、西伯利亚中部 1.14）。
- **待人确认（过目即可）**：这一条是按任务卡做的，但会让上线版和考过试的模型不是同一个，所以请人知晓。

## 4. 全球验证分数（只报告，不用来选）

- 用冻结的 `evaluate.score`，在两个验证窗口上打分。评分单位是训练格子上的示范区矩形和 GFED 矩形（ADR 0004 第 2 条：阶段 G 用 `rect_sets=("demo", "gfed")`）。分三种范围报告：全部、只 GFED、只示范区。按区域给 MALE 和辅助指标，区域年总量偏差按 GFED 区。
- 同一批训练行上同时拟合 M1s（λ = 20）、QM、M0 一起列出；对 M1s 的差用冻结的 `bootstrap_diff`。
- 参照：S11 的窗口模型（只用 3 个示范区训练，参数相同）直接套到全球，只作参照。
- **预先说定**：不论这些分数如何，上线版都是第 3 条的全球重训版。分数不用来挑模型、改参数或改范围；如果全球版在某些区明显不如 M1s，在报告和数据说明里如实写出，交人决定。

## 5. 稳定性区间

- **格子级**：用 S11 封存的 100 次整年重抽（`seeds.resampling`，抽到的年份和 `freeze.json` 逐个核对一致），冻结参数和轮数，每次在重抽的全球训练行上重训，取 5% / 95% 分位数。
- **区域级**：区域 × 月的重抽总量分位数。按 ADR 0008 第 5 条和 S11 测试结果，区间要乘校准系数。
  - 校准系数用冻结的公式（`freeze.interval_scale`），在**全球**两个验证窗口的 GFED 区 × 月总量上重新求，而不是沿用 S11 的 5.37。理由：5.37 是 3 个示范区、示范区模型的数字，换了训练数据和区域大小以后不适用。
  - 这需要在两个验证窗口上也各做 100 次重抽。
  - **待人确认**：这改了区间的校准来源。
- 只算到 GFED 区和六个框这两层；用户自圈区域仍用前 20 次重抽近似（和 v1 一样）。

### 第 5 条补充（2026-11-04）：每组只用前 50 次重抽

- **改了什么**：上线版（deploy）、主验证窗口、辅助验证窗口三组都只用前 50 次整年重抽，不再用 100 次：
  - 格子级 5% / 95% 分位数用这 50 次。
  - 区间校准系数用两个验证窗口各自的前 50 次。辅助窗口已经算了 100 次，只取前 50 次，这样两个窗口用的重抽一样。
  - 代码：`harmonization/series_global.py` 的 `RESAMPLES = 50`。
- **不是新抽的**：这 50 次是 S11 封存重抽（`seeds.resampling`）的前 50 次。随机数按顺序生成，所以第 b 次和 S11 的第 b 次完全相同。代码照样把抽到的年份和 `results/freeze.json` 逐个核对。
- **理由**：运行时间。用 100 次要到晚上 19 点左右才算完，用 50 次当天就能完成。50 次求出的 5% / 95% 分位数只比 100 次稍微抖一些，算是近似。点估计、所有分数和模型本身都不变。前端给用户自圈区域本来就只用 20 次（`docs/data-interface.md`）。
- **什么时候决定的**：在算出任何全球区间覆盖率和校准系数之前。全球验证 MALE（`reports/global-scores.md`）当时已经算出来了，但它只用点估计，和重抽次数无关。
- **谁决定的**：用户批准，由顶层会话（数据分析设计算法）转达，2026-11-04。
- 以后想用满 100 次，只要把 `RESAMPLES` 改回 100，再把剩下的重抽跑完。已完成的不用重算。

## 6. 序列的其余部分和 v1 完全相同

- 来源规则、Terra 桥接、NOAA-20 接续、近实时标记、`est_m0` 都照 `series_v1.build`。
- 桥接和接续比例的拟合范围变成全球：桥接用全部格子，接续用全部训练格子，按 GFED 区做先验。
- 比例只取决于“格子 × 日历月”的总和，所以先按条带求和再拟合。计数是整数，结果和直接在整张表上拟合完全一样（`tests/test_global.py` 核对）。

## 7. 为了算得动而做的实现选择（不改变结果）

- **按纬度分块**：全球稠密表约 8,680 万行，按 10° 纬度带分块写盘（`processed/global/grid/band_NN.parquet`）。
  - `grid.dense_regions` 只加了一个可选参数 `cells`，默认值时行为不变（S15 复现检查照样适用）。
  - 用到的冻结文件（`prepare`、`evaluate`、`harmonize`、`freeze`）一个字没改。
- **相同输入只预测一次**：特征完全相同的格子-月份，模型估计一定相同。大量“格子和邻格都没有 MODIS 火点”的行特征重复，所以每种特征组合只预测一次再铺回去。代码在每个条带上逐值核对，铺回去的特征和原特征完全相同，哈希碰撞就报错。
- **一次转成 float64**：训练输入转成单一 float64 块。LightGBM 拿到混合类型时本来就会转成 float64，数值相同，只是少复制几次内存。
- **重抽分几个进程并行**：每个进程仍用 8 个线程（`harmonize.THREADS`，结果和线程数有关）。每次重抽结果单独存文件，中断后跳过已完成的部分。
  - 两个进程并行时内存不够，出过两次错（长时间运行的进程占用的提交内存越来越大）。所以后来改成一次只跑一个进程，每 20–25 次换一个新进程（`--max-new`），每次重抽后释放模型。结果不变。
