# 0012 S15：一条命令复现的范围和核对方法

## 背景

任务卡 S15 要求“在干净环境里一条命令复现（例如 `uv run python pipeline.py all`），结果与成绩表一致”。计划第 10 节说队友“可以直接下载 Release 数据，也可以用 `pipeline.py all` 从头重建”。具体从哪一步开始、比什么、哪些步骤不能或不该重跑，任务卡没写。

## 1. 两种入口，验收用第一种

- `pipeline.py all --from-release`：从 Release `data-v0` 下载 S05 的网格表（按 Release 的 SHA256 核对），之后的每个阶段都重跑。不需要 FIRMS key，约 2–3 小时。**S15 的验收用这个入口**，在全新克隆、空数据目录里跑。
- `pipeline.py all`：从原始数据开始（FIRMS 年度包、API、GFED，约 50 GB，要 FIRMS key）。代码已串好，但这次**没有完整重跑**，理由：
  - 年度包有 SHA256 锁定，重下后要逐个核对，S02–S05 的验收（比对、行数账、总数守恒）已经做过；
  - 2026 年的数据来自 API，FIRMS 会陆续用标准产品替换近实时数据，重下的结果本来就可能和 2026-11-03 下载的不一样，所以 API 段只报告差异、不当作错误；
  - 下载约 9 GB 加 1 小时限速 API，会占用用户的 FIRMS 配额。

## 2. 不重跑的步骤

| 步骤 | 为什么不重跑 | 怎么保证一致 |
|---|---|---|
| S10 实验循环（37 次） | 它是“搜索”，结果是选出 E028；E028 已冻结在 `harmonize.py` | `freeze` 阶段在两个验证窗口重跑 E028 的冻结程序，分数和参数要与 `scores-s10.json`、`freeze.json` 完全一致 |
| S10 审核 | 依赖实验分支的变体源码 | 审核记录已提交 |
| S11 封卷 | 答卷是冻结文件，重封会改写它 | 重跑测试集的 100 次重抽，逐位比对已封存的答卷 |
| 最终测试 | 只能考一次（红线 1） | 成绩在 `results/final-test/`，由 GitHub 阅卷生成 |
| S12 逐点复核 | 需要清洗后的 S-NPP 点数据，`data-v0` 没有（ADR 0003） | S12 在原机器上做过（426 个区域-月，0 处不一致，记录在 `meta.json`）；从 Release 重建时 `meta.json` 只差这一项，核对时去掉它再比 |

## 3. 核对什么（`pipeline.py check`，37 项）

1. 各阶段会改写的已提交文件（`reports/a5-stats.json`、`judge-check.md`、`scores-v1.json/.md`、`validation.json`、`docs/anomaly-cases.json`）和提交版本逐字相同（忽略换行符）。
2. 两个验证窗口：冻结程序的分数、参数、轮数等于 `freeze.json`，MALE 等于 `scores-s10.json` 里的 E028；校准系数等于 5.37。
3. 测试集：重训的 `est_final` 和 100 次重抽与封存的答卷逐位相同；M1s、QM、M0 也相同。
4. 数据集 v0、v1 的每个文件 SHA256 等于 `results/expected/` 里记录的值（随 Release 一起的文档副本除外，它们在第 1 项里通过 git 比对）。从 Release 起步时没有 S12 逐点复核，`meta.json` 去掉这一项再比；6 个网页用区域文件里嵌着同一份 `meta.json`，就把已发布的复核记录放回去，按 `series_v1` 的写法重新编码，再要求 SHA256 逐位相同（比“去掉再比”更严）。

## 4. 复现中发现并修好的问题

- 下载和导入原来按“已提交的清单 / 账本里有没有这个文件”判断是否做过。在空数据目录里，这会把所有文件都当成已完成而跳过（干净环境里 GFED 一个都没下）。改成看数据目录里有没有实际结果；重新下载的年度包和 GFED 必须和清单的 SHA256 一致，重新导入的年度包必须和账本行数一致。不影响任何已有结果。
- 核对规则原来只给 `meta.json` 处理了“跳过复核”的情况，漏了 6 个嵌着它的区域文件。已补上（见第 3 节第 4 条），并加了单元测试。
